### P2 - Medium

**1. [types.gen.ts — spec-level] `SessionSkillAddData.body` and `ExperimentalEnhanceData.body` are optional, allowing semantically invalid requests**

`SessionSkillAddData` has `body?: { name: string }` — the body itself is optional, meaning the SDK permits calling `skill.add({ sessionID: "..." })` with no body at all. The server would receive no JSON payload and must 400 or behave unpredictably. Similarly, `ExperimentalEnhanceData` has `body?: { text: string, ... }` — calling `enhance()` with no text is semantically meaningless.

The SDK's `enhance()` method compounds this by accepting `parameters?` (fully optional), so `enhance()` with zero arguments compiles cleanly.

- **Root cause**: OpenAPI spec likely marks the request body as optional.
- **Suggested fix**: In the OpenAPI spec, mark the request body as `required: true` for both `/experimental/enhance` and `POST /session/{sessionID}/skill`. Regenerate SDK.

---

**2. [types.gen.ts — generated] Inline anonymous types for `session_skill` shape repeated across 4 locations**

The `Array<{ name: string; added_at: number; token_estimate: number | null }>` shape appears identically in:
- `EventSessionSkillChanged.properties.skills`
- `SessionSkillListResponses[200]`
- `SessionSkillAddResponses[200]`
- `event-reducer.ts:184` (hand-written cast)

- **Impact**: If the shape changes, all inline instances must be found and updated. The generated repetition is expected from codegen, but the hand-written cast in `event-reducer.ts` is fragile — it will silently drift if the spec changes.
- **Suggested fix**: Define a named `SessionSkill` schema in the OpenAPI spec so codegen produces a reusable type. Import that type in `event-reducer.ts` instead of the inline cast.

---

**3. [types.ts:37 — hand-written] Full `content: string` stored in reactive SolidJS store for every skill**

Each skill entry in `State.skill` carries the full `content` field (SKILL.md markdown body). This is held in a SolidJS `createStore` and participates in reconciliation on every sync update.

- **Impact**: Acceptable for a handful of skills today. If skill count grows or content is large (multi-KB), this inflates client-side memory and reconciliation cost.
- **Suggested fix**: Consider lazy-loading `content` on demand when a user opens skill details, rather than including it in the global store. Low urgency — flag for future evaluation.

---

**4. [sdk.gen.ts — generated] `Skill.add()` makes `name` an optional query-style param instead of required body field**

In the `add()` method, `name` is declared as `name?: string` in the parameters object. Since this is the only field in the body and identifies what skill to add, it should be required. A call like `sdk.session.skill.add({ sessionID: "abc" })` compiles but produces a POST with an empty body.

- **Root cause**: Same as finding #1 — the OpenAPI spec doesn't enforce the body as required.
- **Suggested fix**: Fix in OpenAPI spec alongside finding #1.

### P3 - Low

**5. [types.gen.ts — generated] `SessionSkillRemoveResponse` is bare `boolean`, not an object envelope**

The remove endpoint returns `200: boolean` while list/add return `Array<{...}>`. This is a minor inconsistency but follows the pattern of other sub-resource remove endpoints in the SDK.

- **Suggested fix**: No change needed now. Consider `{ removed: boolean }` for future extensibility.

---

**6. [types.gen.ts — generated] `added_at` / `token_estimate` use snake_case in TypeScript types**

Response shapes use `added_at` and `token_estimate` (snake_case). This is consistent across all occurrences and matches the wire format — intentional per project conventions.

- **Suggested fix**: Accept as-is. If the codegen supports camelCase transform for response types, consider enabling it project-wide in a separate effort.
